# ALIGNMENT: 认证升级

## 1. 文档信息

- 项目名称：市集招募平台
- 文档阶段：Align
- 文档日期：2026-05-03
- 文档目标：将“现代化登录与注册升级”收敛为可执行、可审批、可原子化拆解的认证系统方案
- 当前结论：采用 `方案 A`，以 `Better Auth + Prisma + Email + Passkey(WebAuthn)` 为核心，构建“邮箱 + 密码 + Passkey”的现代认证体系

## 2. 项目背景

当前项目的认证链路仍停留在演示环境能力：

- 登录页使用“角色 + 用户 ID”方式登录
- 会话基于自签 JWT Cookie，仅包含 `userId` 和单一 `role`
- 数据模型仅有 `phone`、`role`、`isVerified` 等轻量字段
- 没有邮箱注册、密码、Passkey、验证码、找回密码、设备会话管理
- 中间件只对“已登录用户访问错误角色路由”做纠偏，未完成匿名访问阻断

这套机制足以支撑早期演示，但无法承载正式业务的注册转化、安全基线、账号找回、多角色治理和后续 OAuth 扩展。

## 3. 升级目标

本轮认证升级要达成以下目标：

1. 将演示登录升级为正式的邮箱注册与登录体系
2. 提供 `邮箱 + 密码` 与 `Passkey` 双入口认证能力
3. 将“单账号单角色”升级为“单账号多角色能力”模型
4. 允许摊主与主办方公开注册，管理员保持后台控制
5. 修复匿名用户可进入内部工作区的保护缺口
6. 建立可持续扩展到 OAuth、MFA、设备管理和风控审计的认证基座

## 4. 用户已确认决策

- 决策 1：后续开发默认按“效果优先、技术现代化优先”推进，不以成本为主要约束
- 决策 2：主方案采用 `方案 A`
- 决策 3：认证主入口采用 `邮箱 + 密码 + Passkey`
- 决策 4：账号模型采用“单账号多角色”
- 决策 5：摊主和主办方均可公开注册
- 决策 6：平台管理员不得通过公开注册进入系统

## 5. 核心问题定义

当前系统需要优先解决以下 8 个问题：

1. 用户无法使用邮箱完成正式注册与登录
2. 账号缺少密码找回、邮箱验证和设备级会话管理
3. 当前 `User.role` 模型无法支撑多角色共存与角色切换
4. 主办方与摊主能力无法围绕统一账号渐进开通
5. 匿名访问保护不完整，内部工作区存在越权暴露风险
6. 服务端鉴权与页面层体验未形成统一认证边界
7. 现有演示登录链路与正式身份体系并存，存在迁移与兼容风险
8. 缺少现代认证事件、审计、限流和恢复能力

## 6. 本轮交付范围

本轮方案覆盖以下内容：

- 统一账号体系升级
- 邮箱注册、邮箱验证、邮箱密码登录
- Passkey 注册与登录
- 忘记密码、重置密码
- 会话管理与安全退出
- 单账号多角色能力模型
- 摊主、主办方公开注册和角色开通路径
- 路由守卫、服务端授权、匿名访问阻断
- 演示登录到正式认证的迁移与过渡策略
- 测试、监控、审计和上线门禁要求

## 7. 明确不纳入本轮范围

以下内容在设计中预留扩展位，但不在本轮必须交付范围：

- 第三方 OAuth 登录的正式接入
- 短信验证码登录
- MFA 双因子强制策略
- 企业 SSO / SAML
- 风险评分引擎与设备指纹系统
- 人工 KYC/实名认证闭环

## 8. 用户故事

### 8.1 访客

- 作为新用户，我可以使用邮箱快速注册账号
- 作为新用户，我可以验证邮箱后直接登录并进入角色开通引导
- 作为回访用户，我可以使用密码或 Passkey 登录
- 作为忘记密码的用户，我可以安全地重置密码

### 8.2 多角色用户

- 作为同一账号用户，我可以同时拥有摊主和主办方能力
- 作为多角色用户，我可以在站内切换当前工作上下文
- 作为主办方，我可以补充组织资料后直接使用主办方工作台

### 8.3 平台安全与运营

- 作为系统，我必须阻止匿名用户访问内部工作区
- 作为系统，我必须拒绝未授权角色调用受限接口
- 作为平台，我需要保留管理员后台创建和管理管理员账号的能力

## 9. 功能边界

### 9.1 首版必须具备

- 邮箱注册
- 邮箱验证
- 邮箱密码登录
- Passkey 绑定与登录
- 忘记密码 / 重置密码
- 会话查看与退出
- 多角色能力授予与切换
- 摊主直开通
- 主办方直开通
- 内部工作区路由保护
- 演示登录过渡开关

### 9.2 首版建议增强

- 新设备登录通知
- 最近登录活动展示
- 登录失败限流和冷却提示
- 首次登录引导绑定 Passkey
- 高风险操作二次确认的扩展位

## 10. 技术路线确认

本轮采用以下技术路线：

- 认证框架：`Better Auth`
- 数据层：`Prisma + PostgreSQL`
- 密码算法：`Argon2id`
- Passkey：`WebAuthn / Passkey`
- 邮件能力：事务邮件服务提供商 + 服务端模板
- 会话策略：数据库会话为主，必要时可增加受控短期 Cookie Claims
- 前端交互：Next.js App Router + Server Actions / Route Handlers
- 权限实现：服务端角色能力校验 + 中间件路由守卫双层兜底

## 11. 成功指标

### 11.1 产品与体验指标

- 注册流程从进入表单到完成账号创建不超过 3 个主步骤
- 邮箱验证成功后可在同一会话内直接完成首登
- 密码登录和 Passkey 登录都能稳定进入正确工作台
- 多角色用户可以在站内明确感知当前角色上下文

### 11.2 工程与安全指标

- 匿名用户无法访问 `/organizer`、`/admin` 等内部工作区
- 所有受保护 API 都依赖服务端会话，不再信任客户端注入身份
- 关键认证链路具备测试覆盖：注册、验证、登录、登出、重置密码、角色切换、路由保护
- 现有演示登录可通过显式开关保留，仅用于开发或演示环境

## 12. 风险与控制策略

### 12.1 主要风险

- 数据模型重构会影响现有 `User` 及其关联表
- 登录体系切换会影响现有中间件、页面守卫和测试夹具
- 多角色引入后，原来基于单一 `role` 的页面逻辑将出现语义漂移
- 演示账号、种子数据和正式认证并存期间，容易出现环境差异

### 12.2 控制策略

- 通过迁移脚本逐步引入认证模型，避免一次性切断旧数据
- 先建立新认证基座与兼容适配，再逐步替换页面和 API 入口
- 将角色能力从 `User.role` 拆到独立成员关系，降低后续演进成本
- 用环境变量显式控制演示登录入口是否启用
- 对认证链路实行 TDD，先补测试再切实现

## 13. 验收标准

当以下条件全部满足时，Align 阶段视为通过：

1. 认证升级目标、范围、非目标定义清晰
2. 认证方式、角色模型、公开注册边界全部明确
3. 安全门禁、迁移策略和兼容边界已记录
4. Architect 阶段所需的模块、数据流、异常处理输入充分
5. Atomize 阶段可以据此拆出独立可验证任务

## 14. 结论

当前项目的认证系统应从“演示型身份入口”升级为“正式生产级认证基座”。最合适的路径不是继续扩展现有 JWT Stub，而是以 `Better Auth + Prisma + Email + Passkey` 为中心，重建统一账号、多角色能力、完整会话管理和服务端权限边界，并在迁移期保留受控演示入口，确保业务连续性与安全性兼得。
