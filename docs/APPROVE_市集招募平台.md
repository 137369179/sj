## 4. 当前方案摘要

## 4.1 产品定位

平台定位为“一站式市集经济数字化服务平台”，核心是连接：

- 摊主
- 主办方
- 消费者
- 平台运营方

## 4.2 核心策略

采用双轨方案：

- 终局轨：保留你原始方案中的全角色、全端、服务化、生态化蓝图
- MVP 轨：重构为更适合云端自动开发的最小闭环路线

## 4.3 MVP 目标

MVP 只验证这条业务闭环：

`摊主发现市集 -> 在线报名 -> 主办方审核 -> 摊位分配 -> 通知结果 -> 基础复盘`

## 5. 范围审批

## 5.1 已纳入 MVP

- 账号体系与角色识别
- 主办方创建/编辑/发布市集
- 摊主浏览、搜索、筛选、查看详情
- 摊主提交报名申请与附件
- 主办方查看申请、审核申请
- 摊位配置与基础分配
- 站内通知
- 平台最小审核后台
- 市场级基础看板

## 5.2 明确不纳入 MVP

- 消费者独立产品完整开发
- 线上商城完整交易
- 政府监管系统对接
- 支付、结算、提现全链路
- OCR 自动核验正式上线
- 信用分完整算法
- AI 预测、智能定价、智能推荐正式版
- 原生 Android/iOS/鸿蒙 全端首发

## 5.3 为什么这样收敛

- 避免首期项目范围爆炸
- 保证任务可自动拆分和自动验证
- 避免被终局技术复杂度拖垮
- 用最小业务闭环先验证 PMF

## 6. 技术路线审批

## 6.1 终局轨

保留如下方向作为中长期路线：

- 多端覆盖：App / 小程序 / H5 / PC
- 服务化后端
- 容器化部署
- 数据分析与信用体系
- 合规与生态扩展

## 6.2 MVP 轨

建议采用：

- 前端：Next.js + TypeScript + Tailwind CSS
- 交付形态：主办方 PC 后台 + 摊主 H5/PWA + 平台管理端
- 架构：单仓 + 模块化单体
- 数据：PostgreSQL 或 MySQL + Redis + 对象存储
- 安全：环境变量管理、权限控制、审计日志、审批门

## 6.3 审批判断

若批准本路线，则代表认可以下原则：

- MVP 不强制绑定 Kuikly 作为首期开发框架
- 首期优先统一 TypeScript 技术栈，服务云端自动研发
- 等业务稳定后再向原生多端和服务化演进

## 9. 风险审查

## 9.1 高风险项

- 范围膨胀导致 MVP 失控
- 过早引入多端原生框架导致自动开发困难
- 调度系统设计过重，反而拖慢业务 MVP
- 数据模型若不统一，终局与 MVP 会断层

## 9.2 已采取控制策略

- 以 MVP 闭环强行收敛范围
- 使用双轨方案隔离终局叙事与落地方案
- 任务拆解按中颗粒控制复杂度
- 自动研发设置 A/B/C 级门禁

## 9.3 当前残余风险

- 仍需在实施计划阶段决定首期是否纳入支付
- 仍需决定 MVP 的具体部署平台
- 仍需决定数据库最终选择是 PostgreSQL 还是 MySQL
- 仍需决定身份登录首期是否支持手机号验证码之外的第三方登录
