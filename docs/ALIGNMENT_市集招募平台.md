# ALIGNMENT: 市集招募平台

## 1. 文档信息

- 项目名称：市集招募平台
- 文档阶段：Align
- 文档日期：2026-05-01
- 文档目标：将“市集活动摊主招募 APP 开发方案”收敛为可执行、可审批、可自动化推进的产品与研发边界
- 当前结论：采用“双轨方案”，即“企业终局蓝图 + MVP 自动化落地蓝图”并行设计

## 2. 项目背景

市集经济正在从粗放式增长转向品牌化、规范化、数字化。当前行业存在招募信息分散、审核不透明、摊位分配粗放、经营数据缺失、宣传协同不足等问题。项目目标是建设一个连接摊主、主办方、消费者与平台管理者的数字化服务平台，先建立招募与运营闭环，再逐步扩展到经营工具、信用体系、消费者种草与复购生态。

## 3. 项目愿景

### 3.1 终局愿景

建设一个覆盖摊主、主办方、消费者、平台管理四类角色的一站式市集经济数字化平台，形成：

- 招募与审核数字化
- 摊位规划与分配数字化
- 经营数据与协同营销数字化
- 双向信用与合规管理数字化
- 市集后链路复购与生态服务数字化

### 3.2 MVP 愿景

在最短周期内跑通“摊主发现市集 -> 报名 -> 主办方审核 -> 摊位分配 -> 通知结果 -> 复盘看板”的最小业务闭环，验证平台是否能提升招募效率、审核效率和匹配成功率。

## 4. 双轨策略

## 4.1 终局轨

保留原始方案中的完整业务版图，用于：

- 立项、汇报、路演、融资
- 团队中长期架构规划
- 后续多端、多角色、微服务、生态化扩展的总体参考

终局轨覆盖：

- 摊主端：发现市集、报名申请、资质上传、摊位偏好、经营工具、收益结算、信用分、社群与课程
- 主办方端：发起活动、招商审核、摊位规划、现场执行、运营复盘、财务管理
- 消费者端：发现市集、内容种草、预约提醒、现场互动、线上复购
- 平台端：内容审核、用户管理、风控、信用管理、数据资产运营、商业化管理

## 4.2 MVP 轨

MVP 仅保留下列一级能力：

- 账号体系与角色识别
- 市集创建与发布
- 市集浏览、搜索、筛选
- 摊主报名申请
- 主办方审核与状态流转
- 摊位基础配置与分配
- 站内通知
- 基础运营看板
- 平台管理最小后台

MVP 暂不进入开发范围的能力：

- 复杂智能推荐
- OCR 自动资质核验
- 线上商城
- 社群聊天
- 消费者端独立产品
- 政府系统打通
- 金融、保险、信用评分算法
- AI 预测与动态定价

## 5. 目标用户

### 5.1 核心用户

- 摊主：手作创业者、全职摊主、兼职摊主、餐饮摊主、品牌商家
- 主办方：商业地产、文旅景区、政府/社区、专业策展方

### 5.2 间接用户

- 消费者：通过远期消费者端与专题页触达
- 平台运营人员：负责风控、审核、客服、内容治理、数据管理

## 6. 核心问题定义

平台首要解决的问题不是“把所有角色所有功能一次做全”，而是优先解决以下 5 个高价值问题：

1. 主办方能否高效发布招募并集中收取申请
2. 摊主能否低门槛、透明地找到合适市集并在线报名
3. 主办方能否清晰地审核摊主、管理状态、分配摊位
4. 双方能否在统一平台内看到进度、结果和基础通知
5. 平台能否沉淀结构化数据，为后续推荐、信用和经营分析建立基础

## 7. 产品范围定义

## 7.1 本轮方案交付范围

本轮仅输出完整方案，不直接进入代码开发。交付内容包括：

- ALIGNMENT 文档
- DESIGN 文档
- TASK 文档
- 自动研发流程设计
- 自动研发调度系统设计

## 7.2 后续自动开发的首个建议对象

建议后续以“主办方后台 + 摊主 H5/PWA 报名端 + 基础 API”作为第一批自动化开发对象，而不是直接全端同步开发。

## 8. 技术路线确认

用户已确认技术约束为“可优化重构”，因此本方案采用：

- 终局轨：保留原始多端、服务化、容器化思路
- MVP 轨：重构为更适合云端自动开发的统一技术栈与模块化架构

这意味着：

- 终局不丢
- MVP 不被终局技术复杂度拖垮
- 后续自动化执行更可控

## 9. 成功指标

### 9.1 方案阶段成功指标

- 业务边界无冲突
- MVP 范围清晰且能在单仓内独立交付
- 终局轨与 MVP 轨之间有明确迁移路径
- 自动化流程具备输入、输出、门禁、回滚点
- 任务拆解可被 AI/Agent 独立执行

### 9.2 MVP 业务成功指标

- 主办方入驻数 >= 10
- 已发布市集数 >= 30
- 注册摊主数 >= 500
- 报名转审核完成率 >= 70%
- 审核平均耗时下降 >= 50%
- 市集报名匹配成功率 >= 60%

## 10. 非目标

以下内容不是本轮设计必须完成的目标：

- 一次性定义所有远期 UI 高保真稿
- 一次性设计全部微服务详细接口
- 一次性定义全国化 BD 组织架构与财务模型细节
- 一次性落地完整原生 Android/iOS/鸿蒙客户端

## 11. 关键决策

### 11.1 已确认决策

- 决策 1：当前以“先出全量方案不开发”为目标
- 决策 2：整体路线采用“双轨方案”
- 决策 3：技术方案允许“可优化重构”
- 决策 4：自动化机制同时包含“文档驱动型”和“调度系统型”
- 决策 5：后续方案将服务于云端自动开发，而不是仅做汇报材料

### 11.2 待后续审批决策

- MVP 首期是否选择 Next.js 全栈单仓
- 是否首期接入支付
- 是否首期接入地图
- 是否首期接入资质 OCR
- 是否首期同步输出 PRD、ER、API 附录文档

## 12. 风险与边界

### 12.1 主要风险

- 范围膨胀：把终局能力误纳入 MVP
- 技术失配：为了多端同期上线过早引入高复杂跨端框架
- 自动化失控：未设置审批门禁导致高风险任务被错误执行
- 数据模型漂移：终局与 MVP 使用两套不兼容领域模型

### 12.2 控制策略

- MVP 只保留招募闭环
- 所有远期能力在文档中标注“预留不实现”
- 自动化系统设置人工审批门
- 统一领域模型先行，再做实现分层

## 13. 验收标准

当以下条件全部满足时，Align 阶段视为通过：

1. 项目目标、边界、非目标定义清晰
2. MVP 与终局范围区分明确
3. 用户角色与核心问题定义清晰
4. 成功指标可量化
5. 关键决策已记录
6. 后续 Architect 与 Atomize 阶段具备足够输入

## 14. 结论

本项目不适合“直接全自动完成所有功能”，正确路径是：

1. 用双轨方案保住产品愿景和资本叙事
2. 用 MVP 收敛能力建立真实业务闭环
3. 用自动研发流程和调度系统为后续云端自主开发奠定基础
